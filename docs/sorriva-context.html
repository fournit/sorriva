Sorriva

The intelligent music layer that sits above your hardware and streaming services — the one place that knows your entire music world and delivers it beautifully based on context.

Project Overview

What It Is

  • Unified music graph across local library + every streaming service
  • FLAC at home, Apple Music / Spotify away — seamlessly
  • AirPlay 2 multi-room with saved zone groups
  • AI discovery via Deriva across your full music world
  • Pure App Store product — nothing to install at home

What It Is Not

  • A self-hosted server (no Mac Mini required)
  • A Spotify competitor (you keep your subscription)
  • A hardware company (no Sorriva speakers)
  • A Roon clone (simpler, cheaper, no server)
  • Android (AirPlay 2 is Apple-only — intentional)

The gap nobody fills

Spotify owns the catalog. Sonos owns the hardware. Roon owns the audiophile server. Nobody owns the intelligent layer that unifies all of them into one coherent, beautiful experience. That's Sorriva.

Architecture Pivot — 2026-07-03

Original architecture was a self-hosted Python/Flask server on Mac Mini, positioned as a Roon replacement. Replaced entirely.

2026-07-03 — Key Decisions Locked

  • No self-hosted server — pure App Store product
  • Unified music graph — one track identity, multiple sources
  • Spotify Connect + MusicKit — no app switching
  • Apple ecosystem only — intentional product decision
  • Mac app as optional library bridge (not required)
  • Windows users fully supported — app lives on Apple devices
  • EQService abstraction — one UI, per-device API translation

2026-07-04 — Audio Delivery Architecture Revised

  • Connect protocols (Spotify Connect, Qobuz Connect, Tidal Connect) adopted as primary streaming delivery — device pulls directly from cloud, phone is controller only, full hi-res preserved
  • AirPlay 2 demoted to fallback — used for cross-ecosystem groups and AirPlay-only devices only
  • Zone grouping model locked: Sonos-only groups via Sonos HTTP API (24/48 lossless), Bluesound-only groups via BluOS API (24/192 lossless), mixed groups via AirPlay 2 (16/44.1 lossless CD)
  • Cross-ecosystem grouping (Sorriva advantage): Roon cannot group Sonos + Bluesound at any quality — Sorriva allows it via AirPlay 2 fallback with honest quality labelling
  • "Best quality or everywhere" — the user-facing zone grouping framing
  • Signal Path Indicator feature locked — shows source format, delivery protocol, endpoint quality at all times
  • MQA: not building — MQA Ltd in administration 2023, industry abandoning format
  • Per-device PCM/multichannel config not needed — device and protocol handle automatically
  • Audio quality positioning locked: nobody gets lossy audio in Sorriva (except Spotify at source). Lossless on every path. Hi-res requires Bluesound hardware.
  • music-app-context.md retired — sorriva-context.html is sole source of truth

Unified Music Graph

Every track in the user's world exists once in Sorriva's understanding. Source is just an attribute resolved at playback time. Sorriva owns the playlist, the history, the discovery, the identity.

Track: Kind of Blue — Miles Davis — So What
  └── Sources:
        ├── Local library (FLAC, 24-bit)     ← home, preferred
        ├── Apple Music                       ← away, lossless
        └── Spotify                           ← away, fallback
  └── Sorriva playlists: ["Late Night Jazz", "Favorites"]
  └── Play count: 12 · Last played: Tuesday
  └── MusicBrainz ID: [canonical cross-platform identifier]

Context-Aware Source Resolution

Playback request for a track
        │
        ▼
On home network?
        ├── YES → local library (FLAC/ALAC preferred)
        │           fallback: Apple Music → Spotify
        └── NO  → Apple Music → Spotify
                  (streaming services only — no local library

User never thinks about this. It just plays.

Track Identity Matching

MusicBrainz IDs (MBID) as canonical cross-platform track identifiers. Open matching databases bridge Spotify IDs, Apple Music IDs, and local files. 90%+ match rate on typical libraries. Graceful fallback for live versions, remasters, and regional variants.

Scanner Architecture

Core Principle

The library scanner runs on the iOS/iPadOS device — it reads files directly from the NAS over SMB. There is no server-side scanner. The Apple TV (Phase 6) will become the permanent scanner: always-on, LAN-connected, no background execution limits.

Two Scan Modes

ModeTriggerScopeDevice
Full scanManual ("Scan Now") or new share added — requires user confirmationEntire share — all audio filesDedicated iPad (plugged in, app in foreground)
Incremental scanAutomatic on app foreground, after first successful full scanChanged folders only — detected via FolderStat fingerprintsAny device including iPhone

UNAS Pro SMB Constraint — Critical

The UNAS Pro over WiFi cannot sustain persistent SMB connections across hundreds of files. Sessions degrade randomly causing 15s timeouts. Option A (per-file fresh SMBClient connection, 200ms throttle, 64KB reads) is the stable solution. Option B (persistent connection recycled every N files) was tested extensively and abandoned. Artwork passes use a persistent connection per pass since they run sequentially with larger delays and fewer connections.

Tag Reading Implementation — Option A

Phase 1: Directory walk (SMBClient.listDirectory)
  → Uses high-level SMBClient API
  → Collects all audio file paths + sizes
  → No file reads — fast, NAS-agnostic

Phase 2: Tag reading — Option A (per-file fresh connection)
  → For each file: new SMBClient → login → connectShare → fileReader.read(64KB) → logoff
  → 200ms throttle between files (gives NAS breathing room)
  → 15s timeout via DispatchSemaphore
  → WAV/AIFF skipped — no usable embedded tags, path parsing only
  → ~197–290s for 448 tracks over WiFi

Phase 3: Artwork (post-scan, separate passes)
  → Folder art pass: per-album fresh connection, downloads best folder JPEG
  → iTunes API pass: fills albums still missing art (3s stagger)
  → 30s socket wait: iOS reclaims sockets from scan before embedded pass
  → Embedded art pass: persistent connection for entire pass, reads 1MB per file,
     extracts APIC (MP3) / PICTURE block (FLAC) / covr (M4A)

Tag Parsers

FormatParserKey Fields
MP3ID3v2 (v2.3 and v2.4)TIT2, TPE1, TPE2 (album artist), TALB, TDRC/TYER, TRCK, TPOS, TCON
FLACVorbis Comment (block type 4)TITLE, ARTIST, ALBUMARTIST, ALBUM, DATE, TRACKNUMBER, DISCNUMBER, GENRE
M4A/AAC/ALACMP4 atom parser (moov→udta→meta→ilst)©nam, ©ART, aART, ©alb, ©day, trkn, disk, ©gen
WAV/AIFFPath parsing onlyWAV files skipped for tag reads — no usable embedded tags in typical rips. Path parsing derives artist/album/title from folder structure.

Path Parsing Fallback

When tags are absent, corrupt, or the file format doesn't support them, metadata is derived from folder structure. This is the only strategy for WAV/AIFF.

Expected layouts:
  /Root/Artist/Album/01 Track.flac         → standard
  /Root/Artist/Album/CD 1/01 Track.flac   → disc subfolder (collapsed)
  /Root/Artist - Album - 01 Title.mp3     → flat folder (filename parsed)

Disc folder: regex ^(disc|disk|cd|part)\s*\d+$ (case-insensitive) → collapsed
Track number: regex ^\d{1,3}[\s\.\-–_]+ at start of filename
ALBUMARTIST tag takes priority over ARTIST for album attribution

Path Parsing Limitations

Path parsing produces poor data for compilations, Various Artists, and non-standard folder layouts. It is a Phase 1 stopgap only. Tag reading is the correct solution. The Apple TV scanner (Phase 6) will read tags at full LAN speed and replace path-parsed data.

Incremental Rescan — FolderStat

DB table: folder_stats
  id | sourceId | folderPath | fileCount | totalBytes | scannedAt

On app foreground (scenePhase == .active):
  1. ScanCoordinator.checkForChanges() fires
  2. SMBScanner.statFolders() walks top-level folders (no file reads)
  3. Compare fileCount + totalBytes against stored FolderStat records
  4. Changed or new folders → scanChangedFolders() for those paths only
  5. Never-scanned sources (lastScanned == nil) → skip, require manual confirmation
  6. Interrupted scans (scanState == "error", lastScanned == nil) → surface restart alert

Scan states: "idle" | "scanning" | "error"
On app launch: sources stuck in "scanning" → reset to "error" (interrupted scan detection)

Scan UX

  • Full scan confirmation — warns: takes hours on large libraries, auto-lock will be disabled, keep app in foreground
  • Interrupted scan alert — on foreground after killed scan: Restart or Cancel
  • Auto-lock disabled during scan via UIApplication.shared.isIdleTimerDisabled = true — restored on completion. No screen dimming — user controls brightness.
  • Share card progress — live "Scanning X / Y" counter
  • Scan report — files, tracks, albums, artists, completion time — via share long-press context menu

Artwork Enrichment (Post-Scan)

Source priority (per product spec):
  1. Embedded file tags (deferred to Apple TV scanner)
  2. MusicBrainz Cover Art Archive (Phase 2)
  3. iTunes Search API (current — interim fallback)

iTunes Search API call:
  https://itunes.apple.com/search?term={artist}+{album}&entity=album&limit=1&media=music
  artworkUrl100 → swap to 300x300 (thumb) and 600x600 (full)

Cached to: {documentsDir}/artwork/{albumId}_thumb.jpg
           {documentsDir}/artwork/{albumId}_full.jpg

Staggered 3s between requests (rate limit ~20/min)
Runs via Task.detached after scan completes
UI refreshes progressively via .artworkDidUpdate notification

Apple TV Scanner — Phase 6 Priority Elevated

The Apple TV is the permanent scanning solution. Always-on, LAN-connected, no background execution limits, no SMB read size constraints. When built, it replaces both path-based fallback and 8MB-constrained iOS tag reading. Phase 6 priority was elevated after confirming iOS SMB constraints are fundamental, not fixable by alternative libraries or approaches (URLSession smb:// requires document picker entitlement; no iOS API bypasses the sandbox for direct SMB file reads).

Multi-Room & Zones

Sorriva groups zones using native device APIs — not AirPlay 2. Sonos zones are grouped via the Sonos HTTP API. Bluesound zones via the BluOS API. Each ecosystem handles its own sync at firmware level — the same approach Roon uses. AirPlay 2 is reserved as a fallback for cross-ecosystem groups.

Zone Grouping Model

Sonos-only group (e.g. "Downstairs")
  → Sorriva calls Sonos HTTP API
  → Sonos handles sync natively
  → Quality: 24-bit/48kHz lossless

Bluesound-only group (e.g. "Listening Room")
  → Sorriva calls BluOS API
  → BluOS handles sync natively
  → Quality: 24-bit/192kHz lossless

Mixed group (e.g. "Whole House" — Sonos + Bluesound)
  → AirPlay 2 fallback — only cross-ecosystem option
  → Quality: 16-bit/44.1kHz lossless CD
  → Honestly labelled in UI — user sees quality badge before pressing play

Sorriva advantage over Roon

Roon cannot group across ecosystems at any quality level — a Sonos zone and a Bluesound zone simply cannot play together in Roon. Sorriva solves both ends: best quality within ecosystems, everywhere via AirPlay 2 fallback. One decision, clearly labelled. No protocol knowledge required.

Saved Zone Groups

User creates named groups — "Downstairs", "Party Mode", "Whole House" — once, recalls with one tap. Sorriva automatically selects the best delivery path for the hardware mix. Quality badge shown on every group before playback begins.

Compatible Hardware Ecosystem

Works with any device supporting AirPlay 2, Spotify Connect, Qobuz Connect, or Tidal Connect — essentially all serious audio hardware made in the last five years:

Sonos Bluesound Bang & Olufsen Bowers & Wilkins Devialet KEF Naim Marantz Denon Yamaha NAD WiiM

Audio Quality

Sorriva delivers lossless audio on every path. Nobody gets lossy audio except via Spotify (source limitation, not Sorriva's). Hi-res above CD quality requires Bluesound hardware. The Signal Path Indicator makes this visible at all times.

Quality by Delivery Path

Delivery PathMax QualityLossless?Phone in Path?
Qobuz/Tidal Connect → Bluesound24-bit / 192kHz✓No — device pulls directly
Qobuz/Apple Music → Sonos (native API)24-bit / 48kHz✓No — Sonos pulls directly
Spotify Connect → any zone320 kbps AAC✗ Spotify limitationNo — device pulls directly
Mixed group → AirPlay 216-bit / 44.1kHz✓ lossless CDYes — ceiling is AirPlay 2
iPhone/iPad → headphones / USB-C DAC24-bit / 192kHz✓N/A — device direct

Key Concepts

Lossless means the audio data is mathematically identical to the original — nothing thrown away during compression. FLAC and ALAC are lossless. This is the line that matters most.

Hi-res means above CD resolution (24-bit, 96kHz+). Can also be lossless. Whether humans can reliably distinguish hi-res from lossless CD quality in blind tests is genuinely contested. Sorriva supports it where the architecture allows and is honest where it doesn't.

Lossless CD quality (16/44.1) is excellent audio. It already exceeds human perceptual limits. Not a compromise — just not hi-res.

Non-Features (Architecture makes them unnecessary)

  • MQA support — not building. MQA Ltd in administration 2023. Industry standardizing on FLAC.
  • Per-device PCM bit depth config — unnecessary. Device and delivery protocol negotiate automatically. Only needed in Roon because RAAT pushes audio from a server.
  • Multichannel downmix config — out of scope. Local libraries and streaming services are overwhelmingly stereo.

Device Control · EQService

Audio delivery and device control are two separate, simultaneously running layers. Connect protocols handle audio delivery. Native device APIs handle configuration and EQ.

Sorriva
  ├── Audio delivery layer
  │     ├── Qobuz Connect / Tidal Connect  → Bluesound (24/192)
  │     ├── Sonos HTTP API                 → Sonos zones (24/48)
  │     ├── Spotify Connect                → any Connect device
  │     └── AirPlay 2 (fallback)           → cross-ecosystem groups, AirPlay-only devices
  │
  └── EQService layer     → configuration, EQ, tone controls
        ├── Sonos HTTP API   → bass, treble, loudness, balance, Trueplay
        ├── BluOS HTTP API   → EQ, tone controls, device config
        └── Plain AirPlay 2  → volume only (HomePod, etc.)

Abstraction Principle

One Sorriva EQ UI. EQService translates to each device's native API behind the scenes. Users see one consistent interface regardless of device. New device type = write one driver, UI never changes. Devices without EQ APIs show a reduced panel with an honest explanation — not broken, just honest.

Apple Ecosystem Only — Intentional

AirPlay 2 is the core multi-room differentiator. Android has no AirPlay 2 support. The Android equivalent (Google Cast) has a weaker device ecosystem and would require a parallel architecture — essentially a separate product. Being Apple-first is a deliberate product decision, not an apology. Windows users are fully supported — the app lives on Apple devices; the user's PC is invisible to Sorriva.

Marketing Positioning

The Core Message

Sorriva is the music app for people who care about their system — but are tired of being locked into one ecosystem's idea of how it should work.

Hardware Freedom — Key Differentiator

The two dominant players both use hardware lock-in as a business model. Sonos requires Sonos hardware. Roon requires Roon Ready endpoints. Sorriva's answer is the opposite:

If it supports AirPlay 2, Spotify Connect, Qobuz Connect, or Tidal Connect, it works. A $79 WiiM Mini, a $1,000 Marantz M1, a $3,500 Naim Mu-so, a Bluesound Node into a NAD preamp — user's choice, user's budget, user's taste. No Sorriva hardware to buy. No certification program to join. No Roon Ready required.

Audio Quality — Consumer Education Positioning

The market conflates lossless and hi-res constantly. Sorriva cuts through it with an honest, clear position:

  • Nobody gets lossy audio in Sorriva — except via Spotify, which isn't lossless at the source. That's Spotify's limitation, not Sorriva's, and the Signal Path Indicator shows it clearly.
  • Lossless CD quality (16/44.1) is delivered on every path including mixed-hardware AirPlay 2 groups. Excellent audio — not a compromise.
  • 24-bit/48kHz lossless delivered to Sonos hardware via native Sonos API. Same ceiling as using the Sonos app directly.
  • 24-bit/192kHz lossless hi-res delivered to Bluesound hardware via Qobuz Connect and Tidal Connect. Full resolution, device pulls directly from cloud.
  • Hi-res requires the right hardware. Honest, clear, set before subscription.

2026-07-04-2 — Audio Delivery Architecture & Competitive Analysis

  • Connect protocols (Spotify Connect, Qobuz Connect, Tidal Connect) adopted as primary streaming delivery — device pulls directly from cloud, phone is controller only, full hi-res preserved. AirPlay 2 was never the right backbone for streaming.
  • AirPlay 2 demoted to fallback — used for cross-ecosystem groups (Sonos + Bluesound together) and AirPlay-only devices (HomePod etc.)
  • Zone grouping model locked: Sonos-only groups via Sonos HTTP API (24/48 lossless), Bluesound-only groups via BluOS API (24/192 lossless), mixed groups via AirPlay 2 (16/44.1 lossless CD). Same per-protocol approach Roon uses.
  • Cross-ecosystem grouping is a Sorriva advantage: Roon cannot group Sonos + Bluesound at any quality level. Sorriva allows it via AirPlay 2 fallback with honest quality labelling. "Best quality or everywhere" is the user-facing framing.
  • Signal Path Indicator feature locked — shows source format, delivery protocol, and endpoint quality on every now playing screen. Transparency as a feature.
  • MQA: not building — MQA Ltd in administration 2023, industry abandoning format in favor of standard FLAC.
  • Per-device PCM/multichannel config screens not needed — device and protocol negotiate automatically. Only required in Roon because RAAT pushes audio from a server.
  • Audio quality positioning locked: nobody gets lossy in Sorriva (except Spotify at source). Lossless on every path. Hi-res (24/192) requires Bluesound hardware. Consumer education is a product differentiator.
  • Roon Ready demystified: certification requires RAAT, which requires a Roon Core server. Connect protocols deliver equivalent real-world quality with no server, no certification, no licensed hardware list.
  • music-app-context.md retired — sorriva-context.html is sole source of truth going forward.
  • Three new reference documents created: sorriva-competitive.html, sorriva-product-spec.html, sorriva-audio-quality.html. All in Sorriva brand system.
  • docs-manifest.json created — hub docs registry now live.

2026-07-04 through 2026-07-12 — Swift Pivot & Foundation Build

  • Pivoted from React Native (Expo Bare) to pure Swift/SwiftUI — better native API access for SMB, AirPlay 2, Bonjour, local network, GRDB. React Native bridges too costly for this use case.
  • AMSMB2 replaced with kishikawakatsumi/SMBClient v0.3.1 — AMSMB2 cannot enumerate macOS SMB shares (error code 1 on IPC$, known unresolved limitation). SMBClient handles both macOS and NAS shares correctly.
  • GRDB chosen for SQLite — type-safe, Swift-native, excellent performance.
  • Bonjour hostname sanitization — display names ≠ resolvable hostnames. Strip apostrophes, replace spaces with hyphens to derive .local hostname.
  • Sonos UPnP grouping: x-rincon: (single colon) via SetAVTransportURI to member host works for S2 grouping. x-rincon:// (double slash) fails with 501.
  • NavigationStack deferred — legacy NavigationView in use. Known back-nav slide artifact after add-share save flow. fNavigationStackMigration tracks this. When implemented, replace all local library context menus with SorrivaContextActions factory.
  • Sheets preferred over NavigationLink for fullScreenCover-hosted detail views — NavigationLink inside fullScreenCover is unreliable in SwiftUI.

2026-07-13 — Scanner Architecture Decisions

  • UNAS Pro requires 8MB minimum read size (maxReadSize). Reads smaller than maxReadSize stall indefinitely. Root cause identified from console: "SCAN: TIMEOUT 8s" with no error — server simply does not respond to undersized reads.
  • Two-connection strategy required: separate SMBClient instances for directory walk and file reads. Walk client session state is exhausted after listing hundreds of directories — using the same connection for reads causes failures.
  • DispatchSemaphore used for tag read timeout (not withThrowingTaskGroup). Swift structured concurrency cannot cancel a task blocked on a system call. DispatchSemaphore.wait(timeout:) on a background thread actually interrupts. 60s timeout per file for 8MB reads over WiFi.
  • URLSession smb:// URLs do not work in sandboxed iOS apps without document picker entitlement — investigated and ruled out as alternative to SMBClient.
  • Path parsing adopted as Phase 1 fallback for speed and reliability. Known data quality limitations for compilations and non-standard libraries. To be replaced by Apple TV scanner.
  • Apple TV scanner priority elevated — fundamental iOS SMB constraints (8MB reads, 30s background execution limit) make iPhone/iPad an unsuitable permanent scanner. Apple TV is always-on, LAN-connected, no constraints.
  • FolderStat incremental rescan: per-folder file count + total bytes fingerprint. Foreground trigger checks all source folders, only rescans changed ones. Never-scanned sources require explicit confirmation. Interrupted scans detected on launch (scanState reset from "scanning" to "error").
  • SMB path format for Session.create(): leading slash stripped, forward slashes replaced with backslashes. High-level SMBClient handles this internally; direct Session API does not.
  • SorrivaContextMenu shared component + SorrivaContextActions factory adopted. All context menus across library and services use this pattern. Bottom sheet presentation via .sheet() — matches StationActionSheet behavior. Future implementations must use SorrivaContextActions factory — no custom action sheets.
  • Station delete FK constraint: stations table has child records in station_genres and zone_state. Delete children first before deleting station. zone_state records exist for stations that were ever played in a zone — this was the cause of silent delete failures.
  • Artwork: iTunes Search API is interim fallback only. Embedded tag extraction and MusicBrainz Cover Art Archive deferred to Apple TV scanner. Two sizes cached: 300px thumb and 600px full.
