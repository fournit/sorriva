Local Library Playback

How Sorriva streams local FLAC files to Sonos and Bluesound speakers at full lossless quality — with no dedicated server hardware and no setup beyond what the user already has.

Researched 2026-07-14 Implemented 2026-07-14 – 2026-07-15 Sonos S2 · Bluesound BluOS iOS 26+ · iPadOS 26+
Background
The Problem

Playing a user's local FLAC library through Sonos speakers — with the phone out of the audio path, no dedicated server hardware, and zero setup friction — is an unsolved problem in the industry. Every existing solution requires always-on hardware:

  • Roon — requires a Roon Core running on a Mac, PC, NUC, or $700+ Nucleus 24/7.
  • Bluesound — solved elegantly: the BluOS speaker itself is the SMB client. The hardware is the server. Works only with Bluesound hardware.
  • Sonos native — speakers can fetch SMB files directly, but credential registration was removed from the Sonos app in May 2024. NAS library setup no longer exists in the current Sonos app. Dead end.

Sorriva's product promise is plug and play — nothing to install, no new hardware, pure App Store. This session was a full research effort to find an architecture that delivers on that promise.

Architecture Decision
The Chosen Architecture
x-file-cifs:// Direct NAS Playback. Sonos and Bluesound can fetch files directly from the NAS using x-file-cifs:// URIs. Sorriva registers the NAS share with Sonos once via a CreateObject UPnP call, then queues tracks via AddURIToQueue. Sonos manages its own queue, fetches each file from the NAS as it plays, and advances through the album independently. The phone is a pure remote control — no HTTP server, no iOS background restrictions, screen can be locked, phone calls do not interrupt playback.

The critical insight: the HTTP server does not process audio. It moves raw bytes from SMB to HTTP. The FLAC file that comes off the NAS goes to Sonos byte-for-byte identical. Sonos decodes it internally with its own hardware DAC. The iPad never touches the audio engine.

This is not a workaround. It is a better story than Roon for the mainstream user:

  • Roon — buy a $700 Nucleus or leave a computer on 24/7.
  • Sorriva — your iPad, which you already own, becomes your Core. Plug it in. Open Sorriva. Done.
The one constraint, stated honestly: the iPad must stay on the home WiFi network during local library playback sessions. Screen can be locked. It can be on a charger across the room. It just cannot leave the network. This is a reasonable constraint — it's the same device many users already have as a permanent home controller.
Architecture
Data Flow
── Audio path ───────────────────────────────────────────────────────── NAS (FLAC files, SMB share) │ │ SMBClient reads raw bytes — zero decoding ▼ iPad · Sorriva HTTP server (background audio session, screen locked, on charger) │ │ http://[iPad-IP]:8080/track/[trackId] │ Range request support for seeking ▼ Sonos speaker / zone coordinator │ │ Sonos decodes FLAC internally │ Sonos DAC outputs audio ▼ Audio output · 24-bit/48kHz lossless (Sonos) 24-bit/192kHz lossless (Bluesound) ── Control path (completely independent) ────────────────────────────── iPhone · Sorriva remote │ │ UPnP SOAP on port 1400 │ Volume · Queue · Skip · Zone · Pause ▼ Sonos speaker (responds to commands directly, no iPad involved)

The iPad and iPhone operate on completely separate channels. The iPad serves bytes. The iPhone sends commands. Sonos receives both. They do not need to communicate with each other during active playback.

Audio Quality
Quality Preservation
Bit-perfect. A 24-bit/192kHz FLAC file on the NAS arrives at Sonos as a 24-bit/192kHz FLAC file. The iPad introduces zero quality loss at any stage.

Why the iPad does not degrade quality

The HTTP server reads raw file bytes from the NAS via SMBClient and writes those exact bytes into the HTTP response body. It does not decode the audio. It does not re-encode. It does not touch the iOS audio engine. It is functionally identical to a web server serving a static file — the bytes are opaque payload.

What the iPad HTTP server does NOT do: ✗ Decode FLAC to PCM ✗ Re-encode to any format ✗ Touch AVAudioSession for audio output ✗ Use AirPlay (which would impose 16/44.1 ceiling) ✗ Pass bytes through CoreAudio What the iPad HTTP server DOES do: ✓ Open SMB connection to NAS ✓ Read raw file bytes ✓ Write raw file bytes into HTTP response ✓ Handle Range headers (for Sonos seeking) ✓ Declare background audio session (for iOS lifecycle)

Quality ceiling by hardware

The quality limit is always the downstream hardware, never Sorriva or the iPad:

  • Sonos Era 100, Era 300, Arc, Beam, One — 24-bit/48kHz lossless
  • Bluesound Node, Pulse, NAD BluOS — 24-bit/192kHz lossless
  • Mixed Sonos + Bluesound group via AirPlay 2 — 16-bit/44.1kHz lossless CD (AirPlay 2 ceiling, honestly labelled)
User Experience
Sorriva Core Transfer

The session begins on iPhone — the natural starting point for browsing and queue building — and transfers to iPad, which becomes the permanent Core for the session. One tap.

  1. iPhone: User opens Sorriva, browses library, selects album, picks Sonos zone.
  2. iPhone: Sorriva starts HTTP server, constructs http://[iPhone-IP]:8080/track/[id] URIs, calls AddMultipleURIsToQueue + Play on Sonos coordinator.
  3. Sonos: Fetches from iPhone, playback begins.
  4. User: Opens Sorriva on iPad (both devices now running Sorriva on the same network).
  5. iPad: Detects active Sorriva session via Multipeer Connectivity. "Transfer to iPad" prompt appears.
  6. User: Taps Transfer — one tap.
  7. iPad: Starts its own HTTP server. Queries Sonos GetPositionInfo for current track and position.
  8. iPad: Sends new SetAVTransportURI to Sonos with iPad IP + current track + current position.
  9. Sonos: Continues playing without interruption — seamless handoff.
  10. iPhone: HTTP server shuts down. iPhone is now a pure remote control.
  11. iPad: Screen locks. Background audio session keeps HTTP server alive indefinitely.
  12. iPhone: Can leave the house. iPad serves. Sonos plays.
The transfer tap is a feature, not friction. It is an explicit moment where the user designates the iPad as their home Core for this session. This is a meaningful interaction — the user is making a deliberate choice. It should feel intentional and satisfying, not like a workaround.
iOS Lifecycle
Background Audio Session

When the iPad initiates the HTTP server and sends the first SetAVTransportURI, Sorriva declares an AVAudioSession with category .playback. iOS treats any process holding an active .playback session as playing audio — the same protection that keeps Spotify alive when the screen locks.

iOS will not terminate a process with an active background audio session under normal conditions. The iPad can be locked, screen off, sitting on a charger. The HTTP server keeps running. Sonos keeps fetching.

The one critical rule

The iPad must be the device that started or received the transfer of the session. A background audio session is only protected if the process owns it. The transfer flow ensures the iPad becomes the owner at transfer time — the iPhone's session is released before the iPad's begins.

Edge cases

  • iPad force-quit by user — HTTP server dies, Sonos stops. Sorriva shows a persistent "Serving library" notification that makes force-quit unlikely.
  • iOS memory pressure (extreme) — iOS can terminate background processes under severe memory pressure even with a background audio session. Rare. Sorriva can detect playback stop via Sonos UPnP event subscription and surface a prompt to re-establish.
  • iPad leaves WiFi network — HTTP server still runs but Sonos cannot reach it. Sonos stops. Same behaviour as any network interruption.

What Was Built
fLocalHTTPServer, fLocalSonosPlayback, fScannerDuration, and fAlbumQueue are complete. x-file-cifs:// direct NAS→Sonos playback confirmed working: full album queue, both tracks played completely, screen locked, zero iOS involvement after queuing. NAS share registration via CreateObject UPnP call (port 1400) confirmed — no Sonos desktop app or mobile app required. iOS background restriction confirmed: HTTP server suspended on screen lock on both iPhone and iPad regardless of AVAudioSession or charge state. x-file-cifs architecture eliminates this constraint entirely.

SorrivaHTTPServer.swift — NWListener implementation

GCDWebServer was evaluated and discarded — its SPM package does not expose a linkable product. Telegraph was tried and discarded — it buffers the entire response before sending, which causes UNAS Pro SMB connections to hang waiting for the full file. The final implementation uses Apple's native NWListener (Network framework) for raw TCP control, enabling true streaming.

── Critical discoveries during implementation ────────────────────────── UNAS Pro 8MB read limit on persistent connections: The UNAS Pro drops persistent SMB connections after exactly 2 sequential 8MB reads. Streaming dies at offset 16MB every time. Fresh-connection-per-chunk does NOT solve the problem: Opening a new SMBClient per 1MB chunk accumulates orphaned SMB sessions on the NAS. Sessions don't close immediately — they pile up across play attempts and starve new connections, causing silent hangs at inconsistent offsets (6MB, 10MB, 12MB, 18MB, 20MB). Increasing distance each run = old sessions timing out between tests. Correct solution — one persistent session, 1MB sequential reads: Login once. connectShare once. fileReader once. Read 1MB chunks sequentially until EOF. UNAS Pro is stable with 1MB reads on a persistent connection. Confirmed: 44MB FLAC streamed completely. This matches how Roon operates — one SMB connection, sequential reads. Chunk size: 1MB. 8MB chunks: UNAS Pro drops connection on the 3rd read (at 16MB). 1MB chunks on persistent connection: works for any file size. Tested: 44MB and 73MB FLAC, both played completely. Sonos URI error 714 (Illegal MIME type): Sonos rejects plain /track/[uuid] URIs with error 714. Fix: append file extension — /track/[uuid].flac SorrivaHTTPServer strips the extension before SQLite lookup. DIDL duration must not be zero: SetAVTransportURI with duration="0:00:00" causes Sonos to stop after buffering a short segment. Pass empty CurrentURIMetaData instead. Sonos plays to EOF with no duration declared. Only include duration when a valid value exists in DB (populated by scanner).

HTTP server protocol details

  • TCP listener — NWListener on port 8080, all interfaces
  • Request accumulation — reads TCP until \r\n\r\n or \n\n header terminator (Sonos uses either)
  • Response — Content-Length with actual file size, Accept-Ranges: bytes, Connection: close
  • Backpressure — each chunk send awaits .contentProcessed before reading next SMB chunk
  • Background audio — AVAudioSession .playback with .mixWithOthers keeps process alive when screen locks

LocalPlaybackService.swift

  • Starts HTTP server on first playback request if not running
  • URI format: http://[WiFi-IP]:8080/track/[trackId].[ext]
  • Empty CurrentURIMetaData — Sonos plays to EOF without duration declaration
  • SOAP calls via nonisolated static methods on ZoneDiscoveryService to avoid main actor deadlock
  • playTrack and playAlbum implemented; album plays first track — full queue via AddMultipleURIsToQueue is next work

Known remaining issues / next work

fXFileCIFS (next session). Wire x-file-cifs:// into LocalPlaybackService / Playback Conductor. Replace HTTP-based local playback for Sonos/Bluesound zones. Programmatic NAS share registration via CreateObject. Zone capability detection.
fLocalNowPlaying. Mini player and Now Playing do not update for local tracks. ZoneDiscoveryService GetMediaInfo returns empty CurrentURIMetaData for local HTTP URIs and x-file-cifs URIs. Fix: LocalPlaybackService pushes track metadata directly to zone state after initiating playback.

No new SPM dependencies

GCDWebServer (no linkable SPM product) and Telegraph (full-response buffering incompatible with streaming) were both evaluated and rejected. The final implementation uses only Apple-native frameworks: Network, AVFoundation, and the existing SMBClient package.

Bluesound
Bluesound Native Path
Bluesound hardware is its own SMB client. The BluOS player — Node, Pulse, Vault — connects directly to the NAS via SMB and fetches files itself. No HTTP server needed. No iPad bridge. No phone involvement after initiating playback.

For Bluesound users, local library playback is architecturally superior to Sonos:

  • Sorriva calls the BluOS HTTP API: http://[player-IP]:11000/Play?url=[SMB-path]
  • BluOS player opens its own SMB connection to the NAS
  • Phone is completely out of the audio path — same as a radio stream
  • iPhone or iPad can leave the house — BluOS keeps playing
  • Quality ceiling: 24-bit/192kHz lossless (BluOS hardware)

Bluesound users get the full Roon-equivalent experience — local library at full quality, phone as controller only — with zero additional hardware and zero setup beyond what Sorriva already does for SMB scanning.

This is a genuine competitive advantage. Roon cannot group Sonos + Bluesound at any quality level. Sorriva delivers local library at 24/192 on Bluesound and 24/48 on Sonos, with honest quality labelling and the same unified library UI for both.
Future
Future Paths

fMacBridge (already on roadmap)

An optional Mac menu bar app that runs as an always-on library bridge. Exposes local library as an HTTP server on the home network. Eliminates the iPad constraint entirely for Mac users. Sorriva detects the bridge and uses it automatically — iPad path becomes unnecessary when bridge is running. Power user path, not required for core experience.

Sonos SMB credential registration (research item)

The Sonos app must make some UPnP or proprietary HTTP call to a speaker when registering a NAS share. This call has never been documented or reverse-engineered publicly — likely because every third-party developer assumed it was impossible and used the Sonos app instead. A Wireshark packet capture during NAS share setup in an older Sonos app version could reveal this call. If identified, Sorriva could register NAS credentials programmatically — making x-file-cifs:// viable without any Sonos app involvement. This would eliminate the iPad requirement for Sonos users entirely. Worth investigating if Sonos ever restores the NAS setup UI in their app.

NAS HTTP for Synology / QNAP users

Users with Synology or QNAP NAS can enable Web Station to serve files over HTTP directly. Sorriva could detect and use this path automatically — no iPad bridge needed for those users. Detect during SMB source setup: try an HTTP probe to the NAS IP, if it responds with the file, use HTTP path. Fall back to iPad proxy otherwise. Additive optimization, not a baseline requirement.

Automatic Core selection

Long-term: if both iPhone and iPad are home, Sorriva automatically selects the iPad as Core with no transfer tap needed. Requires detecting which device is on charger and has been stationary (CoreMotion + charging state). The transfer tap remains as the explicit path; automatic selection is a quality-of-life enhancement.
